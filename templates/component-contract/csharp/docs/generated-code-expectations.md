# Generated-code expectations — __Prefix__ (C#)

The semantic bar this repository holds Specfuse-generated code to. Two
readers: a person reviewing a regen PR, and the generator's consumer-QA
reviewer, which reads this file from inside a clone of this repo and treats
the five section names below as a stable interface
([`CONSUMER-CONTRACT.md`](https://github.com/clabonte/generator/blob/main/docs/CONSUMER-CONTRACT.md)).
Keep the headings; add what you like under them.

`gen-contract.yml` is the mechanical bar: rule IDs, `file:line`, identical on
every run. This file is what "acceptable" means beyond it. When a review
finding here turns out to be mechanically checkable, the durable fix is a new
rule in `gen-contract.yml`, not a longer list in this file.

## Markers

Every generated file is a `.g.cs` under a `gen-src/` folder, opens with
`#nullable enable`, and carries the `<auto-generated>` header block with the
`Generated by the Specfuse Generator` line. That header is what excludes the
file from analyzers and formatters; the folder and the extension are what the
regen's clean step keys on. Enforced by `GEN-001` to `GEN-005`.

## Layering

`__Prefix__.Domain` depends on nothing in the solution. `__Prefix__.Infrastructure`
depends on Domain. `__Prefix__.Api` depends on Domain and references
Infrastructure only to wire it up in `Program.cs`. Enforced over generated
`using` lines and over the project references by `GEN-010` to `GEN-014`.

## Build wiring

`Directory.Build.props` turns default globbing off and compiles exactly
`src/**/*.cs` and `gen-src/**/*.cs` in every project. The generator's
`*.generated-paths.json` path manifests are committed, never git-ignored.
Enforced by `GEN-020` and `GEN-021`.

## Extension points

Hand-written code extends generated code four ways, all in `src/`:
`partial` classes in the generated type's namespace, concrete classes derived
from a generated `*Base`, the `partial` mapper-hook methods, and a custom
service registered after `AddServices()` to replace a generated default. A generated
file is never copied into `src/` and edited (`GEN-030`). A generated base is
always adopted: a handler or job interface is never implemented directly, and
a gated application service always derives from its
`{Tag}ApplicationServiceBase` (`GEN-040` to `GEN-042`).

## Integration contract

Hand-written code depends on these generated surfaces. A rename or removal
here breaks the app even when the generated tree itself compiles:

- Concrete handlers, jobs and application services derive from generated
  `*Base` classes and interfaces; DI registration resolves them by the
  generated interface, never by a concrete type the generator does not emit.
- Hand-owned EF migrations are derived from the generated
  `EntityTypeConfiguration<T>` classes: a column rename that arrives without
  `x-legacy-names` in the spec silently orphans persisted data.
- Hand-written tests consume the generated fakes and builders (`A.Order()`,
  `TestSeed.OrderId`); a builder surface change goes through the generator's
  one-cycle deprecation shim, never disappears outright.
- Generated controllers call `UserHelper.GetUser(User)`; generated functional
  tests derive from `ApiTestBase` and call `CreateHttpClient(role)` and
  `EnsureFakeData()`. Those types are hand-written here and must keep those
  members.

## Standing expectations

- A fresh `dotnet build` succeeds on regenerated output with zero edits.
- Entity and EF configuration agree: every property a configuration
  references exists on the entity, and every mapped column has a property.
- Navigations are configured on both sides with matching shapes, never twice
  with conflicting ones.
- Builder defaults survive a real insert: no required field defaulted to
  null, no string default longer than its declared max length.
- The generated authorization tests reflect the spec's `x-roles` exactly.

## Accepted quirks — do not re-report

- Per-package `CHANGELOG.md` files inflate the regen diff; that is their job.
- `_Deprecated` builder shims linger exactly one regen cycle by design.

## Do not report — the gate already decides these

Run `./scripts/check-gen-contract.sh --list` first. These are settled by rule
ID and `file:line`, identically on every run; a review finding that duplicates
one is noise.

### Do-not-report table

| Do not review | Rule |
|---|---|
| `.g.cs` extension, gen-src placement, foreign files under gen-src | `GEN-001`, `GEN-004`, `GEN-005` |
| `#nullable enable` present | `GEN-002` |
| auto-generated header block | `GEN-003` |
| Clean Architecture layering in generated code and project references | `GEN-010` to `GEN-014` |
| `Directory.Build.props` compile roots, ignored manifests | `GEN-020`, `GEN-021` |
| generated header in a hand-written file | `GEN-030` |
| unadopted `*Base` classes, direct handler-interface implementations | `GEN-040` to `GEN-042` |

What remains is the judgement: does the regen do what was asked, and does it
break something no rule states yet. Removals are the highest-risk content of
a regen and nothing mechanical catches them: a generated file, type or member
that disappeared needs its hand-written call sites listed, or an empty list
after actually looking.
