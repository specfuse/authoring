# Setting up component repos

[Getting started](getting-started.md) covers the **spec repo**, where you author, validate, and run the generator. This guide covers the other side: the **component repos** (backend service, mobile or web app, Python services) that receive the generated code. It sets out a layout and a set of conventions that a multi-repo project runs on in production. Adopt them as they are, or use them as a checklist when you choose your own.

## 1. The model: the spec repo pushes, components receive

Component repos never run the generator, fetch the jar, or check out the specs. Generation runs **from the spec repo** and writes into each component through the `destination` of each group in the project file (see [`Project_File.md` §8.6](../handbooks/Project_File.md#86-destination)):

```
~/work/hello-orders/
├── hello-orders-specs/        spec repo: specs, hello-orders-project.json, .specfuse/state/
├── Backend/                   C# service
├── hello_orders_app/          Flutter app
└── hello-orders-ai/           Python services
```

```json
{ "name": "Domain",   "language": "C#",     "basePackage": "HelloOrders.Domain", "destination": "../Backend/",                  "cleanGenerated": true },
{ "name": "AppCore",  "language": "dart",   "basePackage": "hello_orders_core",  "destination": "../hello_orders_app/packages/", "cleanGenerated": true,
  "cleanScope": ["hello_orders_core/lib/domain", "hello_orders_core/lib/data"] },
{ "name": "Contracts","language": "python", "basePackage": "hello_orders_contracts", "destination": "../hello-orders-ai/libs/contracts/src", "cleanGenerated": true }
```

What this layout requires:

- **Every repo is a sibling checkout under one parent directory.** The `../` destinations only resolve when the repos sit next to each other. Write the layout down in each component's README, and in your dev-environment repo if you have one, so a new contributor clones them correctly.
- **Run the generator from the spec repo root.** CLI paths resolve against the JVM's working directory ([`Project_File.md` → Working directory](../handbooks/Project_File.md#working-directory-and-path-resolution)), so running from anywhere else writes into the wrong tree.
- **A regen writes into other repos, and it deletes.** With `cleanGenerated: true` the group's generated subtree is wiped before it is rewritten. Before you regen, check that each target component is on a branch you can throw away and has no uncommitted work. Prefer naming specific groups over regenerating all of them.

## 2. Keep generated and hand-written code apart

Each component should have one place where generated code lives, which nobody edits, and a separate place for hand-written code that builds on it. The generator's clean step is built around this split. Files outside the wipe target are never touched ([§8.9](../handbooks/Project_File.md#89-cleangenerated)), so hand-written code is safe as long as it stays outside.

| Language | Generated code lives in | Hand-written code extends it through |
|---|---|---|
| C# | `gen-src/` folders inside each project, files `*.g.cs` with an `<auto-generated/>` header. `Directory.Build.props` compiles `gen-src/` and `src/` together. | `partial` classes in `src/`, generated `*Base` classes you derive from, mapper hook partials. Exclude `gen-src/` from coverage. |
| Python | `_generated/` packages (default wipe target) | Your `handler.py` / `composition.py` beside the generated `handler_base.py`; subclass, don't patch. |
| Dart / Flutter | A dedicated package (e.g. `packages/hello_orders_core`) owned entirely by the generator | Extension methods in the app's `lib/`; screens, view models, and navigation stay in the app. |
| TypeScript | A dedicated package (e.g. `packages/hello-orders-core`) | Import only through the package's `exports` map; never deep-import its files. |

Rules worth writing into each component's README and agent instructions (`CLAUDE.md` / `AGENTS.md`):

- **Never hand-edit generated code.** A wrong generated file is fixed in the spec or the generator, then regenerated. Hand edits disappear on the next regen with `cleanGenerated`.
- **Check the generated package before writing a model, DTO, repository, or client by hand.** It usually already exists.
- **`cleanScope` lists only generated folders.** Name the generated folders one by one, never a parent folder that also holds hand-written files. A pattern like `*/scenarios` is not supported and silently cleans nothing ([§8.10](../handbooks/Project_File.md#810-cleanscope)).

## 3. Wire the generated code into the build

Generated code ships as source inside the component, so it joins the component's normal build:

- **C#:** the `gen-src/` folders belong to existing projects; no extra project references are needed.
- **Dart:** add a path dependency in the app's `pubspec.yaml`:
  ```yaml
  dependencies:
    hello_orders_core:
      path: ./packages/hello_orders_core
  ```
- **Python:** make the generated libraries members of a [uv workspace](https://docs.astral.sh/uv/concepts/projects/workspaces/):
  ```toml
  [tool.uv.workspace]
  members = ["libs/*", "tools/*"]

  [tool.uv.sources]
  hello-orders-contracts = { workspace = true }
  ```
- **TypeScript:** an npm/pnpm workspace package referenced by name.

**Post-generation steps.** Some languages need a step after the generator runs:

- **Dart:** the generator writes `part '*.g.dart'` / `part '*.freezed.dart'` directives but does not run `source_gen`, and the clean step deletes the old outputs. Run `dart pub get && dart run build_runner build --delete-conflicting-outputs` inside the generated package before you analyse or commit it.
- **Lockfile:** if the post-step rewrites the app's `pubspec.lock`, restore it unless the regen meant to change dependencies.

Run these from the spec repo's generate wrapper as soon as the group finishes, so the component tree is never left half-built (see §5).

## 4. Commit the generated code

Commit generated code in the component repo. Every regen then shows up as a reviewable diff in a component PR. CI and teammates build without Java or generator access. And a spec change and its effect on each component are visible side by side.

Ignore the generator's volatile bookkeeping files, such as the per-group `*.generated-paths.json` manifests. The Dart package may need its own `.gitignore` exception if the app ignores `*.g.dart` at the root.

**What a green build does not prove.** A regen can change a field's name or an enum's wire value while every hand-written type that mirrors it still compiles. When you review a regen PR:

1. Diff the changed generated models **by file name, not by path**. A moved file reads as a delete plus an add and hides the field-level change.
2. Diff each enum's **values**, not only its member names.
3. Diff operation parameter lists and request/response shapes.
4. Trace every hand-written type that mirrors a generated one.

## 5. The regen flow

1. **Spec change merges** in the spec repo.
2. **Regen on a branch.** From the spec repo root, bundle, then generate each affected group. The jar's `--group` takes one name, so loop:
   ```bash
   ./scripts/specfuse/bundle-spec.sh api/specs/v1/openapi.yaml output/openapi-bundled.yaml
   # plus ./scripts/specfuse/bundle-async-spec.sh if the project declares asyncSpecifications
   for g in Domain AppCore; do
     specfuse authoring generate generate --group "$g" hello-orders-project.json
   done
   ```
   The first `generate` is the kit command and the second is the generator's own command. Dropping the second one runs the jar with no command. Run any post-generation steps (§3).
3. **Open one PR per component** containing only the regen and its required follow-ups. Review it as in §4.
4. **Merge each component PR.**
5. **Advance the changelog baseline** in the spec repo (§6).

Keep the steps in this order: the spec PR first, then the component PRs, then the baseline. A component PR that lands before the spec change it was generated from makes `main` depend on a spec that isn't on the spec repo's `main` yet.

## 6. Advance the `stateDir` baseline only from merged component code

The generator keeps one file per group under `stateDir` (default `.specfuse/state/<group>.json`, see [§2.4](../handbooks/Project_File.md#24-statedir)). Each regen's `CHANGELOG.md` is diffed against it, so it must describe the code that **shipped on the component's `main`**, not whatever a local regen just produced.

- **Never commit `.specfuse/state` from a spec branch or a local regen.** A baseline committed ahead of the component's `main` adds phantom "Breaking" entries to every later changelog. A stale one makes the next changelog repeat old changes.
- **After a component regen PR merges**, check out a clean `main` in that component that matches `origin/main`, then re-capture the baseline from the code on disk. The generator's `baseline` command regenerates nothing:
  ```bash
  specfuse authoring generate baseline --dry-run hello-orders-project.json
  specfuse authoring generate baseline hello-orders-project.json
  ```
- `baseline` rewrites every group's state file, so restore the files for groups whose component was not on a clean, merged `main` (`git checkout -- .specfuse/state/<group>.json`). Commit the rest in a spec-repo PR on its own (no spec changes), citing the component PR and commit.
- `baseline` rewrites only `<group>.json`. If `<group>.paths.json` has drifted too, it takes a real regen whose output matches the component's `main` byte for byte.

## 7. Contract checks in the component (optional)

A component can also guard its generated tree mechanically, with a CI check that fails when generated files are hand-edited or don't meet the shape the component depends on, plus a short doc describing that expected shape. Tooling for this is not shipped by the kit yet ([#171](https://github.com/specfuse/authoring/issues/171)). Until it is, keep any such check small and specific to the component.
